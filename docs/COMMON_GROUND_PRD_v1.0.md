# COMMON GROUND
## 产品需求文档 PRD v1.0

**不必相信同一个未来，也能共同完成一件事。**

英文定位：Turn conditional market rights into funded, authorized, verifiable public action.

版本：v1.0 ｜ 技术资料核验：2026-09-10 ｜ 目标：Somnia × DreamDEX Event Contracts 可运行原型

产品负责人决策：以 COMMON GROUND 为产品名；Common Trigger 是其中的自动触发能力，不再作为独立产品。首版购买一项真实的开源维护服务。资金规则、授权边界和验收流程按本文固定；上线以集成验证门禁通过为准。

## 01｜产品摘要与研究命题

COMMON GROUND 是一个条件式公共行动产品。参与者将同一 DreamDEX 市场的结果份额交付给共同计划：互补份额合并成基础预算，在市场结算前启动任务；独立的追加份额在市场正式结算后，只有满足既定结果、预算和交付前提，才能启动追加任务。

**核心公式不是“市场上涨，AI 随便执行”，而是“授权一致 + 实际资源足额 + 状态有效，才允许固定行动”。**

首版研究命题：不同参与者可以不统一对未来的判断，但能否通过明确交付的条件权益，在不扩大任何人的授权、不让组织者任意支配资金的前提下，为一个共同任务提供预算并完成交付？

产品不从持仓推断人的真实信念，不承诺赚取收益，也不让 BTC 的方向决定某项公共服务是否值得存在。公共价值由参与者事先认可；市场只决定一部分资源是否可用。

### 最终取舍

| 项目 | v1.0 决策 |
|---|---|
| 核心场景 | 社区资助一项固定范围的开源回归与权限检查 |
| 资金结构 | 基础 Up、基础 Down、一个方向的追加份额，三本独立账 |
| 触发结构 | 基础足额即进入可激活状态；正式结算后按条件追加 |
| 履约结构 | 固定执行者、固定报价、固定验收者；验收后领取 |
| 首版上限 | 一个计划绑定一个市场；一个基础任务 + 至多一个追加任务；最多 32 个贡献地址 |
| 平台费用 | 0；部署、运行与触发费用由运营方单独承担并披露 |
| 排除项 | 新代币、交易策略、概率触发、任意任务市场、通用仲裁、跨链、复杂 AI 编排 |

## 02｜用户、场景与真实动作

### 目标用户

| 角色 | 场景与需求 | 现有摩擦 |
|---|---|---|
| 社区支持者 | 已持有事件结果份额，愿意支持自己使用的开源工具 | 不愿先变现再转账，也不愿把资金交给组织者自由处置 |
| 项目发起人 | 为一个公开代码版本购买小范围检查 | 重复协调筹资、确认用途、追踪任务与核对付款 |
| 服务执行者 | 接受范围和报价清楚的维护任务 | 担心没有预算或验收标准临时变动 |
| 验收者 | 核验产物是否符合固定交付清单 | 输入、版本、执行环境与报告不一致，难以复查 |
| 社区使用者 | 不出资也能读取公开维护结果 | 常常只看到转账或宣传，没有可复现产物 |

### 首个真实服务：Community Maintenance Check

基础任务：针对预先固定的 repository commit、测试集和运行镜像，执行基础回归与权限配置检查，输出机器可读 JSON、测试日志和人类可读报告。范围仅包括列出的检查项。

追加任务：针对同一代码版本运行另一组预先固定的边界、异常处理或配置检查。它是额外工作，不是把基础报告换个标题。

**发现失败测试或风险，不等于服务交付失败。**只要执行了约定的全部检查、完整记录结果并满足可复现要求，发现问题的报告也可通过验收。不得为了获得报酬而要求“所有测试必须绿色”。

链外真实动作是运行程序并交付可复查产物。自动建立 GitHub issue/PR 仅为后续功能，且须取得目标仓库授权；首版不以一条通知或一段 LLM 摘要替代真实工作。

## 03｜产品范围与非目标

### P0 必须交付

一个完整计划从发布、接收真实份额、合并基础预算、启动基础任务、核验产物到支付；一个正式市场结果触发的追加分支；失败、作废、资金不足和超时的退出流程；完整链上与链下证据页面。

资金必须经过本文约束，不通过团队个人钱包人工代持来伪装合约托管。至少完成一次真实网络集成及真实程序运行，其余市场分支允许在明确标注的本地测试中验证。

### P1 可以后续加入

Somnia 链上 Reactivity 自动回调、多个执行者竞价、独立验证者组合、更多任务模板、持有者授权的自动 issue、发现更多同类计划、可配置的退款权重。

### 不做

不做“市场概率超过阈值就花公共资金”；不自动下注或滚仓；不强迫普通捐赠者买结果份额；不证明现实世界的一切事实；不声称全面审计、无风险筹资或保证交付；不将不同市场或不同计划的份额混用；不通过自买自卖制造采用率。

首版不支持支持者仅认捐、不转入资产的承诺。也不支持“我不同意提前合并，但把我当作共同预算”的模糊模式。不同意本计划条款的人不参与基础桶，可另建新计划。

## 04｜技术事实与集成门禁

DreamDEX 官方将事件合约开发入口定义为 `@somnia-chain/markets-sdk`；普通现货 HTTP API 不能代替事件合约开发接口。其完整结果份额具备铸造、合并及结算赎回能力。[S1]

### 必须按官方实现核对的边界

| 事实 | 开发约束 |
|---|---|
| 同一市场完整份额可合并 | 只能合并属于同一已绑定市场的正确结果 ID；不能仅凭名字匹配 [S2] |
| 合并在 Trading 状态开放 | 每次写操作以链上实时状态为准，并检查本计划更早的截止时间 [S2] |
| 池子在不同窗口复用 | 主键至少是 chainId + module + marketId，不以 pool address 单独识别市场 [S2] |
| 结果资产采用共享 ERC-6909 | 按 token contract + tokenId 查余额、授权、转入；不是独立 ERC-20 [S2, S6] |
| 作废每份按 0.5 处理 | “作废”不是按用户购入成本退款；方案须单独处理 [S3] |
| SDK 和网络精度不同 | 固定经过测试的版本；按部署及代币元数据处理精度，禁止浮点资金计算 [S1, S4] |
| 外部核心合约可升级 | 本项目计划不可修改，不代表所有外部依赖不可升级；上线前记录部署与实现版本 [S4] |

### G0：开始完整开发前的三项闸门

G0-A：钱包真实结果份额能通过已核验授权方式转入项目合约；项目合约能以自己的资产和调用身份合并，实际抵押资产进入同一个受约束金库。

G0-B：项目合约能读取绑定市场的终态，并赎回自己持有的追加份额，支付资产不经过团队个人钱包。核对胜、负、作废及错误市场处理。

G0-C：执行服务能运行一个固定检查模板、产出可读取报告，并由独立于执行者权限的验收服务复核。

每项保存交易、余额前后差、部署网络、ABI/package 版本和产物。SDK 里有 EOA 示例，不构成“自建合约一定可直接调用”的证明。官方 ABIs 从已锁定 SDK 取得，逐项核对方法签名和资金接收语义。[S4]

任一关键闸门失败，不得用数据库余额或假交易维持“已打通”展示。可以继续本地验证，但发布页必须停止对应真实资金入口。

## 05｜合并后的核心机制：三桶记账，双阶段行动

为避免“哪些人的份额被优先合并、失败时退给谁”的歧义，首版不动态分配混合库存，固定三类贡献桶。

| 资金桶 | 接收资产 | 用途 | 上限 |
|---|---|---|---|
| BASE_UP | 指定市场 Up | 与 BASE_DOWN 等量配对，为基础任务筹资 | Qb |
| BASE_DOWN | 指定市场 Down | 与 BASE_UP 等量配对，为基础任务筹资 | Qb |
| BONUS | 计划指定的一个方向，Up 或 Down | 正式结算后有条件资助追加任务 | Qx |

Qb、Qx 是按实际结果份额精度处理的量；预算 B、X 是抵押资产最小单位。部署门禁必须验证它们的换算与输出，不能假设两种代币的原始整数天然相同。

基础两桶都足额时，只合并 Qb 对一次，得到对应基础预算 B。将实际收入锁定为基础任务预算，不支付给发起人。最后一笔存入只说明“已足额”，真正激活及合并交易确认后才能显示“基础任务已获预算”。

BONUS 从开始就单独标记，不能被拿去补基础缺口。基础任务可以先启动；追加份额在固定收集截止前仍可接收，但不得超上限。市场正式结算后，只有追加方向获胜、实际可用预算不少于固定价格 X、基础任务已获验收、且未超过追加决策截止，才能启动追加任务。

任何一项不满足，不临时降低任务范围、不借用其他桶、不要求补钱、不交给管理员自由决定。按照对应退出规则处理。

### 数字示例（演示配置，非真实报价）

基础任务 B = 80 单位测试抵押资产；基础 Up 与 Down 各需要 80 份。追加任务 X = 40，追加方向为 Up，追加桶最多 40 份。

甲交付 80 份 BASE_UP 和 40 份 BONUS；乙交付 80 份 BASE_DOWN。总资产是 120 Up + 80 Down，但两种 Up 在内部用途与退款账本上不同。

基础 80 + 80 合并为 80，锁定任务预算并启动真实检查。追加的 40 Up 留存：Up 获胜且其他条件满足时赎回 40、启动追加检查；Down 获胜则不追加；作废时按官方规则产生 20，全部进入追加桶退出分配。[S3]

“共同部分现在做，条件部分到时做”，不表示零风险；它仅移除了已合并部分对市场方向的依赖。

## 06｜计划与授权：不可变、同用途、可审阅

### Plan Manifest 必须包含

| 字段组 | 固定内容 |
|---|---|
| 身份与网络 | schemaVersion、chainId、campaignAddress、planHash、module、venueId、marketId |
| 资产 | outcomeToken、upId、downId、collateral、精度与换算配置 |
| 任务 | 基础与追加的 taskSpecHash、repoCommit、suiteHash、runnerImageDigest、artifactSchema |
| 金额 | Qb、Qx、B、X、bonusSide、平台费 0、退款方法版本 |
| 角色 | 固定执行者、收款地址、验收者；三者职责分别展示 |
| 时间 | fundingDeadline、baseStartGrace、runDuration、reviewDuration、bonusDecisionDeadline |
| 边界 | 允许提前合并、基础失败禁止追加、作废不追加、单任务固定价、无主观仲裁 |
| 退出 | 原份额退出条件、合并后退款权重、舍入方法、无管理员没收未领取款 |

发起人在草稿阶段可以修改。执行者确认报价与交付期，验收者确认任务清单后，部署不可变计划；发布后修改任何影响资金或交付的字段，都要创建新计划，不能沿用旧支持者授权。

支持者入金交易须显式带 planHash、bucket 和金额。预览页说明“我交付的是该结果权益，不只是结果出来后再决定的认捐”，并展示提前合并和默认退款权重。

交易由钱包直接签名即可作为首版授权，不强制再加一次离线签名。执行者/验收者可以链上确认计划；将来采用 EIP-712 离线消息时，必须加入域隔离、有效期及重放保护。[S7]

**没有共同用途，即使份额互补也不合并。**不同计划地址天然隔离，不用 LLM 推断两个不同用途“差不多”。

## 07｜时间规则与并发

所有金额用整数，所有业务截止用链上 Unix 秒。界面显示用户本地时间和 UTC；不把其他接口的毫秒或纳秒直接当成本计划时间。

| 时间规则 | v1.0 行为 |
|---|---|
| 入金与基础激活 | 要求 `now < fundingDeadline` 且官方市场仍为 Trading |
| fundingDeadline | 必须早于市场 expiry，并预留在目标网络实测的安全余量；创建时展示余量 |
| 已足额但未激活 | 支持者在合法阶段仍可退出；以实际链上交易顺序为准，不保证待处理交易优先 |
| 截止时基础未激活 | 转入失败退出；即使市场仍 Trading，也不继续延长或擅自合并 |
| 基础激活后 | 基础份额不可退出；追加桶在其收集截止前仍可按规则撤回 |
| 任务启动 | READY 后在 startGrace 内由固定执行者确认；否则超时 |
| 提交与验收 | 提交不得晚于 submitDeadline；验收不得晚于 reviewDeadline；过期操作无效 |
| 追加等待 | 允许市场先结束、基础任务后验收；两者都满足才能追加 |
| bonusDecisionDeadline | 提前固定，必须覆盖合理的基础任务周期；到期后不再启动新追加任务 |

迟到的市场结算不能复活已经到期取消的追加行动。若已取消但追加份额仍未变现，支持者可取回对应结果份额，自己选择后续赎回，不必等待本产品处理。

基础资金转化前的“足额待激活”和转化后的“任务已锁定”是两个不同状态，界面、通知和后台不得混用。

## 08｜资金归属与退款：首版固定规则

### 各种情况到底退什么

| 情况 | 基础桶处理 | 追加桶处理 |
|---|---|---|
| 基础未激活，用户合法撤回 | 退相应数量的原结果份额 | 同理退原份额 |
| 基础未激活且到期/窗口不再可用 | 所有人领取尚未使用的原份额 | 原份额退出，计划不再继续 |
| 基础已合并，任务验收通过 | 基础预算成为执行者应收款 | 等待官方结果及追加条件 |
| 基础任务拒绝或超时 | 未承诺给已验收任务的基础抵押资产按既定权重退回 | 取消追加；未赎回则退份额，已赎回则退实际抵押资产 |
| 追加方向获胜且满足全部条件 | 不受影响 | 锁定 X；追加验收后支付 |
| 追加方向获胜但不足价/过期/基础未通过 | 不受影响 | 不做半个任务；可用资金全额进入该桶退款 |
| 追加方向失败 | 不受影响 | 无保证现金退款；可领取残留的原失败份额，不花钱做无意义的零支付赎回 |
| 市场作废 | 已成功合并的基础预算不因方向改变 | 不启动追加；按实际赎回收入分配 |
| 追加任务拒绝或超时 | 不受影响 | 未支付的追加预算退给追加贡献者 |

### 已合并基础资金的退款权重

首版采用明确约定的“双边各 50%”：基础任务失败时，上涨桶支持者共有基础剩余资金的一半，下跌桶支持者共有另一半；每边再按实际贡献份额比例分配。

这只是双方事先接受的分摊规则，**不是对 Up 与 Down 市价相等的断言，也不是按原始购入成本退款**。不同意此方法的人不加入该计划。后续才研究按协商权重分配。

本版任务全额验收或不验收，不做部分结算。所以基础退款池通常为 B 或 0，追加退款池为实际尚未承诺支付的收入。不得在验收通过后仍把执行者的应收款算成可退款余额。

### 精确舍入，不遗留可被管理员提走的尘埃

每个退款池形成时冻结该池金额与贡献快照。基础上侧池为 `floor(R/2)`，下侧池为余数。每边按贡献地址首次登记顺序，计算累计份额区间：

`claim_i = floor(R_side * cumulative_i / Q_side) - floor(R_side * cumulative_before_i / Q_side)`

追加退款池同法按追加份额分配。最多 32 个地址，可以有界计算；顺序、公式与快照时间写入规则。领取顺序不影响已分配金额，所有分配之和必须恰好等于该池金额。

退款采用主动领取，固定返回已登记贡献者；不提供管理员扫走已登记未领取资产的功能。零金额领取不发送无意义交易。原始份额、抵押资产和任何直接误转但未登记的资产不能混成同一账。

直接向合约地址转入资产不自动构成有效贡献。必须经过入金函数登记；首版不承诺恢复所有误转资产，界面明确禁止裸转。

## 09｜角色与权限矩阵

| 角色 | 允许做什么 | 明确禁止 |
|---|---|---|
| 发起人 | 编辑草稿、公布计划、补充不影响条款的说明 | 发布后改规则、提取受约束资金、更换收款人 |
| 支持者 | 审阅并按桶贡献；在允许阶段退出；领取归属自己的剩余资产 | 以一个计划的授权操作另一个计划；追回已支付服务费 |
| 执行者 | 预先接受计划；领取 READY 任务；提交产物；领取已验收报酬 | 修改市场结果、改变任务、替验收者批准自己 |
| 验收者 | 对特定证据版本批准或拒绝，提交原因 | 改报价、随意收款、越过时限批准旧证据 |
| 自动触发服务 | 读取状态，发送无须许可的激活、结算同步与到期处理交易 | 决定市场输赢、改计划、把资金转到自己的地址 |
| 普通第三方 | 调用安全补执行入口、核对证据 | 指定任意调用或任意受益人 |
| 运营方 | 部署、供给自己的 gas、运行服务、暂停网站新增计划入口 | 修改已生效计划、停止已存在的合法退出权 |

支持者原钱包中的资产，除明确授权转入的份额外，不应被访问。优先使用具体 ERC-6909 tokenId 和数量的授权，避免无限 operator。ERC-6909 与 ERC-1155 不同，标准不要求接收回调，必须通过显式入金函数记账，不能依赖接收钩子自动登记。[S6]

本产品是智能合约托管，不是“资金永远没有离开用户”。合约、外部协议、验收者、运行服务、报告存储均有各自的信任边界。

## 10｜状态机：计划、市场与任务分开

### 计划资金状态

`OPEN → BASE_ACTIVE → FINISHED`

或：

`OPEN → FUNDING_FAILED → REFUNDABLE`

BASE_ACTIVE 只说明基础资产已转换并锁定预算，不说明市场已结算，也不说明任务完成。基础失败、追加跳过和最终款项归属以任务与资金桶状态组合计算，不挤进一个模糊的 success 字段。

### 官方市场状态

`Listed → Trading → Locked → Resolved / Voided`

它只从官方市场状态读取。链下数据库是投影，不是裁判。官方的中间枚举、索引字符串及 on-chain 状态值可能不同，适配层必须显式映射。[S2]

### 单个任务状态

| 状态 | 进入条件 | 下一步 |
|---|---|---|
| WAITING | 尚未满足资助或前置条件 | READY 或 SKIPPED |
| READY | 预算已在合约内锁定 | 执行者在 startGrace 内 start |
| RUNNING | 固定执行者确认接单 | 提交证据或到期 |
| SUBMITTED | 当前证据摘要、清单与位置已记录 | 验收者批准、拒绝或到期 |
| ACCEPTED | 验收者在时限内批准当前摘要 | 资金从任务保留转为执行者应收 |
| REJECTED | 验收者给出明确拒绝原因 | 预算进入退款池 |
| EXPIRED | 启动、提交或验收超过对应期限 | 预算进入退款池 |
| SKIPPED | 方向不符、作废、预算不足、基础失败或追加截止 | 无新任务；追加资产按规则退出 |

任务付款不是新的验收；`paid` 独立记录。ACCEPTED 之后即使执行者晚些领取，也不允许因时间过去而退款给支持者。

首版每项任务只接收一次正式提交，不做无限修订与重新报价。运行服务可以在提交前内部重试，但不能延长合约时间窗。人工争议、上诉和部分验收不在 v1.0。

### 追加动作的判定顺序

先检查是否已取消/启动/终结，防止重入重复；再检查基础是否失败、是否达到追加决策截止；随后读取官方终态并按需赎回。只有获胜、资金足额、基础已验收、仍在期限内四项同时满足才变为 READY。

市场先结算而基础尚未验收时，追加收入记为待决资金，不付款也不提前退款。基础随后失败或追加期限届满，待决资金进入追加退款池。基础后来才通过，也不能复活已经取消的追加任务。

## 11｜用户流程与验收条件

### F-01 创建并发布计划

发起人选择受支持的真实市场，系统核对剩余时间、网络、资产和当前状态。填写固定任务模板、报价、三个桶的上限及退款规则；执行者和验收者确认后发布。

验收：计划可导出；planHash 与合约字段一致；关键字段缺失不能发布；用户可以在付款前看到完整规则；已发布计划不能原地改写。

### F-02 参与支持

支持者看到自己持有的对应份额，选择基础侧或追加桶，查看最坏情况与退出权。只授权必要数量，并由入金交易确认实际转入，记下所属桶。

验收：错误 chainId、错误 marketId、错误结果 ID、错误 planHash、超上限、零金额、超截止均拒绝；浏览器刷新后链上余额和贡献账仍一致。

### F-03 基础任务激活

触发服务发现两桶足额，发起无须许可的 activateBase。合约再次检查时限与官方状态，锁住贡献快照、执行一次合并、检查实际抵押资产余额增加，并锁定固定预算。

验收：合并失败则整个激活事务回退；不产生虚假的 READY。只有一次成功激活；重复调用不能再次燃烧资产或再次创建任务。

### F-04 实际执行

执行者在允许时间内确认任务。运行器按固定 commit、image 和 suite 获取允许的代码快照并隔离运行。生成结构化报告、完整日志、输入与环境摘要。

验收：真实进程已运行；日志与报告对应同一个 taskId 和 runId；任务不要求测试全通过，而要求诚实、完整地记录执行结果；产物可读取。

### F-05 验收与付款

验收服务验证固定输入、检查集合、产物完整性与必要的可复现结果。独立的验收地址批准或拒绝当前 evidenceHash。批准后执行者自行领取固定款项。

验收：只有指定验收者可决策；批准绑定具体 taskId、证据摘要和有效期限；旧结果不可用于新任务；不能重放付款。执行者与验收者地址必须不同，但这不能证明现实中由不同人控制。

### F-06 结算及追加行动

监听官方市场终态，核验结果，按计划赎回追加份额，再根据第 10 节判定是否启动追加任务。

验收：前端不能自行选择 Up/Down；没有真实赎回收入时不显示可花预算；作废或资金不足不能执行半价任务；基础未验收不能越级追加。

### F-07 退出与恢复

用户在贡献页面查看可领取的原份额或抵押资产以及形成原因，自行调用领取。自动服务断线后，任何人都可以调用安全的超时、同步或推进函数。

验收：自动服务离线不会赋予管理员额外权力；退出无需发起人批准；同一权益不能既退原份额又领抵押资产；验收后的劳动报酬不被退款覆盖。

## 12｜链外执行与验收规范

### TaskSpec

固定 repository URL 或代码包地址、commit/hash、运行镜像 digest、依赖锁文件摘要、suiteHash、允许读取的链上快照、运行资源上限、产物 JSON schema、验收地址和判定规则。

基础与追加任务各有独立的 TaskSpec；追加不是“AI 看结果临时决定做什么”。最多一个追加任务，方向和价格提前写死。

### 最低产物集

`result.json`：taskId、planHash、repoCommit、runnerDigest、suiteHash、开始与结束时间、完整检查项、pass/fail/skip/error、退出码及必要输入快照。

`execution.log`：标准输出和错误摘要，敏感字段按固定规则移除。

`report.md`：解释执行范围、发现、无法验证的项和重跑方式。

`manifest.json`：各产物的字节摘要与可读取位置；链上提交其 evidenceHash。建议以规范化 manifest 的 keccak256 绑定验收，文件校验方法写入 manifest，不混用未声明的 hash 算法。

### 验收不是“报告好看”

检查 TaskSpec 一致、产物能下载、指定检查实际覆盖、输出内部一致、可复现的关键项可被重复验证。输入代码存在 bug 可以得到合格的风险报告。伪造绿灯或静默跳过检查不合格。

首版采用一个事先指定的验收者。它可能误判、离线或与执行者串通，这是明确的中心化信任点。协议限制其可批准的任务、金额和时间，却不能从链上独自证明线下质量。

### 执行安全

只接受经过批准的公开测试仓库/代码快照。运行器处于短生命周期隔离环境，无钱包、API 密钥、宿主写入权限和不必要外网访问；固定 CPU、内存、磁盘、运行时间和输出尺寸上限。普通容器不是运行任意敌对代码的充分隔离保证；未来开放任意仓库前需更强沙箱和安全评估。

签名与广播进程独立于执行沙箱。产物页面净化 HTML/Markdown，外部 URL 防 SSRF；不让测试输出成为系统指令。报告中的建议不会自动修改主仓库或转移其他资金。

### 离线与履约风险

验收者沉默不等于批准。验收期限后可到期退款，因此诚实执行者也可能因验收服务故障而未获报酬。执行者在接受计划时须看到这项风险；首版用可复现任务与值守验收降低风险，而不假装解决了通用仲裁。

```text
Next.js / React 客户端
  计划审阅、贡献、状态、证据、领取
                 |
                 v
CommonGroundCampaign（每计划独立合约）
  不可变计划 + 三桶账本 + 任务托管 + 退出权
                 |
                 v

  查询市场 / 合并完整份额 / 赎回结果权益

链上事件 -> Indexer / Trigger Worker -> 受限推进交易
                         |
                         v
                 独立执行沙箱
                         |
                         v
                  产物存储 / 验收服务
                         |
                         v
                    链上验收与领取
```

### 首版技术选择

| 层 | 建议实现 | 约束 |
|---|---|---|
| 前端 | Next.js、React、TypeScript、钱包连接 | 主流程不要求中心化账号；钱包不自动改链或签名 |
| 合约 | Solidity + Foundry | 每计划隔离，非可升级；不提供任意 call 或任意收款 |
| DreamDEX | 锁定 markets-sdk + viem，核对导出的 ABI | SDK 用于发现与开发；资金动作由金库正确调用官方接口，不借团队 EOA 中转 |
| 后端 | Node.js / TypeScript | 只做索引、产物编排和允许的推进；不能宣布市场结果 |
| 数据 | PostgreSQL | 任务与事件投影、游标、产物索引；不是资金真相 |
| 执行 | 持久工作队列 + 隔离运行器 | 重启可恢复；输出与任务唯一绑定 |
| 产物 | 可公开读取的对象存储 + 内容摘要 | 不宣称永久可用；至少覆盖整个评审与约定保留期 |
| 自动化 | P0 链下监听、历史补读、定期对账 | 每次写入仍由合约核验；任何人可补执行 |
| P1 | Somnia 链上 Reactivity | 在核验接口和原生代币费用后加入；不替代链外执行者 [S8, S9] |

官方地址页区分 Somnia 主网 5031 与测试网 50312，并列出 USDso 与测试抵押资产的不同精度。部署配置必须按目标网络核验，不复制另一网络的金额常量；官方核心地址相同也不代表网络或市场相同。[S4]

### 故障恢复

链下订阅断开后会消失，节点不补发断线期间遗漏事件；恢复服务必须保存区块游标，并用日志补读对账。[S8]

事件唯一键采用 chainId + txHash + logIndex；任务唯一键采用 campaignAddress + taskIndex。收到重复消息可以重新核验，但不能重复记账或付款。链下运行采用“至少一次处理 + 幂等任务”，不宣称分布式系统绝对只执行一次。外部副作用需要自己的幂等键或重复检查。

区块确认策略按目标链验证后配置。浏览器和工作器均展示最近确认高度与数据新鲜度；数据不一致时停止新增有风险动作，不伪造“最终完成”。

## 14｜自建合约接口建议

以下均为本项目设计的接口名，不是 DreamDEX 已有方法。具体签名以实现评审为准，不在业务文案中假装已经存在。

| 接口 | 主要要求 |
|---|---|
| confirmExecutor(planHash) / confirmVerifier(planHash) | 发布前由对应角色接受固定条款 |
| depositContribution(planHash, bucket, amount) | 具体 tokenId 转入、差额核对、限额与期限检查、分桶登记 |
| withdrawContribution(bucket, amount) | 仅在仍拥有原份额退出权时允许，不能用追加资产退基础 |
| activateBase() | 无须许可；固定市场、截止、两侧足额、一次性合并、实际入账及任务 READY |
| failFunding() | 未激活且已到期或明确无法继续时，停止计划并开放原资产退出 |
| syncMarketAndBonus() | 读取官方状态、按需且仅一次赎回、处理追加条件，不接受前端输赢参数 |
| startTask(taskIndex) | 固定执行者、READY 状态、有效启动窗口 |
| submitEvidence(taskIndex, evidenceHash, uri) | 固定执行者、一次提交、正确任务、提交期限 |
| decideEvidence(taskIndex, evidenceHash, accepted, reasonHash) | 固定验收者、当前摘要、有效时限；终态不可改写 |
| claimTaskPayment(taskIndex) | ACCEPTED 且未支付，只给计划固定 payee |
| expireTask(taskIndex) | 无须许可，严格检查当前状态和对应 deadline |
| closeBonus() | 基础失败或追加决策截止等条件下停止追加，保留剩余资产归属 |
| claimRefund(refundBucket) | 依据已冻结的份额归属及池金额，领取自己的原资产或抵押资产 |
| getPlan() / getPosition(account) / getTask(index) | 返回规则、可领取项与证据状态，支持不依赖主前端的读取 |

合约状态先更新再外部转账，增加重入保护。每个币种和结果 ID 的真实余额应不小于尚未完成的相应负债。不得通过任意地址调用、任意 calldata、管理员紧急提款绕过固定计划。

只允许来自已核验部署的资产和协议；fee-on-transfer、rebasing 等会破坏账本假设的资产不纳入首版。依赖升级或返回值偏离时应失败关闭，退出只承诺仍可按底层协议完成的范围，不替外部协议失效提供保证。

## 15｜账本不变量与事件

### 结果份额守恒

对每个 bucket 和 tokenId：

`已登记存入 = 当前未用余额 + 已用于合并 + 已用于赎回 + 已退原份额`

BASE_UP 与 BONUS 即使共用同一个真实 Up tokenId，也必须有独立负债记录。不能因为总余额足够，就挪用另一桶。

### 抵押资产守恒

对登记在计划内的每一笔合并/赎回实际收入：

`总实际收入 = 任务保留 + 执行者应收 + 退款应付 + 累计已支付 + 累计已退款`

本版平台费为零，gas 在计划之外。未登记误转不参与这一等式；物理余额可能更大，但不能将其计成用户筹资成功。ACCEPTED 转换保留金为执行者应收，EXPIRED 转换保留金为退款应付，同一笔钱不能同时处于两边。

### 核心事件

PlanPublished、RoleConfirmed、ContributionDeposited、ContributionWithdrawn、BaseActivated、FundingFailed、MarketObserved、BonusRedeemed、TaskReady、TaskStarted、EvidenceSubmitted、TaskAccepted、TaskRejected、TaskExpired、PaymentClaimed、RefundPoolFinalized、RefundClaimed。

每条记录关联 campaign、marketId、planHash 或 taskId，并能链接交易与实际产物。链上事件证明已发生的合约动作；链下报告证明范围依赖验收方法，不能混为一种“已验证真相”。

## 16｜页面与交互要求

### 页面 A：计划列表与创建

显示任务内容、代码版本、目标预算、可立即激活进度、绑定市场与截止。创建只开放经过验证的任务模板，不允许任意脚本上传。参与者数按钱包地址称呼，不称为独立真人。

### 页面 B：共同计划详情（产品核心）

顶部固定显示一句人能理解的目标；中间显示三桶实际资产及授权用途；底部显示任务时间线、参与条款、验收者与退出规则。

主指标不用收益率：使用“基础任务还差多少互补份额”“已锁定多少服务预算”“追加条件是否满足”“真实工作进度”。份额数量不能误标成用户已经捐出的稳定币金额。

### 页面 C：支持与签署

展示“本次交付的资产、允许用途、是否允许提前转换、最多损失的已交付权益、合并后不可撤回、失败时采用的退款方法”。确认具体市场与额度，再进行必要授权和入金。拒绝签名时不写成功记录。

基础两侧退款各 50% 的条款必须显著展示，不能埋在展开说明里。钱包余额与合约贡献余额分开。

### 页面 D：行动与证据

左右并列官方市场状态与公共任务状态。支持出现“市场仍交易，基础检查正在运行”。展示真实 runId、固定输入、下载产物、验收理由和付款状态；测试网或回放有明显标签。

### 页面 E：我的权益与退出

逐桶显示原份额可取回数量、已用于任务的贡献、抵押资产应领金额、形成原因和操作费用。零支付显示“此份额不产生现金支付”，不显示令人误解的“退款成功”。

浏览器无法联网时显示数据时间而非绿色成功。自动服务停止时出现“等待推进/可自行推进”按钮；按钮调用同一套受约束合约接口。

### 页面 F：执行与验收工作台

只允许对应角色看到可执行按钮；角色限制必须由合约再次检查。执行者看到截止与固定任务，验收者看到当前 evidenceHash 和判定清单，不能一键批准所有未看结果的任务。

### 关键文案

“已足额，等待合并确认”不写成“已支付”；“预算已锁定”不写成“工作已完成”；“验收者确认交付”不写成“数学证明结果完全正确”；“退回原结果份额”不写成“保本退款”。

## 17｜数据模型、API 与产物目录

### 链下最小数据表

| 表 | 关键字段 | 约束 |
|---|---|---|
| plans | id、chainId、campaignAddress、planHash、marketId、manifest、publishTx | chainId + campaignAddress 唯一；规则以合约为准 |
| contributions | planId、account、bucket、amountRaw、txHash、logIndex | 按事件幂等写入，不用前端请求直接增余额 |
| tasks | taskId、planId、kind、status、deadlines、evidenceHash、paid | planId + taskIndex 唯一；链上终态优先 |
| runs | runId、taskId、attempt、inputHash、runnerDigest、timestamps、result | 多次内部尝试可记录，但正式提交最多一次 |
| artifacts | runId、kind、uri、digest、size、availability | 下载后可重新校验摘要 |
| decisions | taskId、evidenceHash、verifier、decision、reasonHash、txHash | 仅展示真正上链的验收结论 |
| chain_events | chainId、blockNumber、blockHash、txHash、logIndex、payload | 完整保存；对账和重建来源 |
| worker_cursors | chainId、contract、lastConfirmedBlock、updatedAt | 支持断线补读与区块重组策略 |

所有金额以十进制字符串/大整数保存，不转成 JavaScript Number 或数据库浮点数。所有时间存 UTC；对外展示同时保留网络与区块语境。

### 自建 HTTP 接口建议

`GET /plans`、`GET /plans/:id`、`GET /plans/:id/positions/:address`、`GET /tasks/:id`、`GET /tasks/:id/evidence`、`GET /health` 为读取接口。

`POST /drafts` 只保存草稿；`POST /runs/:id/artifacts` 接收经授权的产物。任何链下写接口都不能直接给用户增加余额、把任务改成已验收，或产生已付款事实。

合约交易由钱包或专门的受限广播进程发出。鉴权签名绑定用途、nonce、期限和请求摘要，不能把登录签名当作资金授权。

### 上线完成定义

G0 全部通过；P0 状态与资金测试通过；至少一条官方真实市场的基础资金闭环及真实任务完成；正式结算分支有真实链上证据，其余分支可用标注清楚的测试；产物可下载；所有资金在支持者、任务应收或退款账本中可对账。

测试网络的成功不直接等于生产资金安全。接受真实公众资金前需要独立合约审查、依赖升级策略、运行与密钥管理评估、当地适用要求评估，以及更长的故障演练。

## 19｜研发计划：以验证门禁为顺序

下面是开发工作量分配示例，不代表当前赛事仍有 48 小时提交窗口。活动状态与正式截止需另行核验。

| 阶段 | 优先交付 | 完成判据 |
|---|---|---|
| 0–6 小时 | G0：真实份额转入金库、合并、赎回；固定 runner 实验 | 有余额前后差、ABI 与可读取真实产物；不通过则不做精装修 |
| 6–16 小时 | 固定计划、三桶账、基础一次性激活、原份额退出 | 基础资金状态与失败路径单测通过 |
| 16–26 小时 | 基础任务托管、提交、验收、领取；隔离运行器 | 一个真实基础任务完成并取得付款证据 |
| 26–34 小时 | 追加分支、作废/失败/过期处理、退款快照 | 资金不串用，结果晚到不会复活任务 |
| 34–40 小时 | 计划与支持页面、证据页、个人退出页 | 陌生用户能解释条款并完成主要流程 |
| 40–44 小时 | 断线恢复、权限、精度、竞态与安全测试 | 核心失败清单通过，成本有记录 |
| 44–48 小时 | 部署、文档、演示、证据归档 | 链接可访问，链上与真实动作对应，运行标签准确 |

单人开发或基础集成复杂时应增加实际工期，不以删除真实资金校验、验收和退出规则来伪装“完成”。可以砍多计划创建器、动画、排行榜、链上 Reactivity 和自动 issue；不可砍三桶隔离、真实合并、正式结算、任务交付及失败退出。

建议分工：合约/链上集成一人，执行与数据一人，前端与证据展示可由两人协同。若只有一人，先 CLI 跑通所有核心行为，再做页面。

## 21｜产品价值验证与商业路径

### 原创性边界

完整结果份额合并是既有原语，事件触发自动化也不是本项目首创。研究贡献定位在“授权一致的条件权益，如何组织成真实公共任务并承担交付责任”，不宣传发明了新概率学或首次让市场影响现实。[S1]

### 三个必须验证的假设

H1：已有结果份额持有者愿意交付部分权益，用于共同认可的任务，而不只是直接转稳定币。

H2：提前匹配能够减少等待和协调，让真实任务更快获得足额预算。

H3：明确的交付与退出规则，能提高参与意愿，且额外操作成本没有抵消收益。

用直接捐款、条件式捐款、本产品三种流程作小规模用户对照。记录实际参与意愿、用户理解、所需操作、启动时间和总成本；不只记录“觉得很酷”。如果直接捐款始终更好，应收窄到已经持有条件权益且需要该结构的用户，不诱导所有人绕路。

### 指标

有效计划数、独立贡献地址数（非独立真人）、实际匹配金额、基础任务启动时间、验收通过与到期比例、退款可领取成功率、公共产物被使用情况、真实执行成本、重复使用意愿。

不把团队测试流量当自然采用，不将结果份额数量等同于交易额，也不为了奖金生成无意义交易。

### 收费

原型不抽佣，执行者报酬按固定任务价。后续可研究透明的任务服务费或组织者托管工具订阅，任何费率都必须在新的计划中提前披露，不影响旧承诺。无需发行治理币或信誉代币。

### 与评审标准对应

| 维度 | 交付证据 |
|---|---|
| 创新与原创性 20% | 两阶段行动、授权兼容、原语新用途；不只监听结算 |
| 技术实施 25% | 真实市场、份额合并、赎回、状态隔离、权限和退款测试 |
| 用户体验 20% | 一眼看懂做什么、什么被允许、资金如何使用及退回 |
| 商业及生态影响 20% | 真实服务需求、真实支持者、现有权益的非纯投机用途 |

以上四项共 85%，沿用讨论中提供的标准；不补造剩余评分项，也不把方案潜力写成已获得成绩。

## 附录 B｜决策日志

D01：COMMON GROUND 为产品，Common Trigger 为触发能力。

D02：首版只为真实开源维护任务筹资，不以宏大现实场景掩盖验证困难。

D03：先合并可立即支持基础任务的互补权益；正式结算只决定追加资源。

D04：用三个明确用途桶取代不透明的“总 Up/Down 库存”，避免贡献排序与退款歧义。

D05：基础双方合并后退款权益固定各半；必须显著告知，不冒充市价估值。

D06：一个计划只允许一个追加方向和一个固定任务；资金不足不临时改价或减配。

D07：基础验收通过是追加的必要前提；基础失败不会继续花追加资金。

D08：付款由明确验收触发，沉默不等于验收；首版保留并披露单一验收者信任。

D09：P0 用可靠工作器与无须许可补执行保障流程；链上 Reactivity 是可增强项，不用它掩盖链外依赖。

D10：不发币、不替用户判断未来、不自动交易、不把操作者离线说成所有系统仍必然运行。
